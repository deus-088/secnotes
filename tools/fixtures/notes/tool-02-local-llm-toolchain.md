# 本地开源大模型驱动安全工具链的部署要点

## 一、为什么要本地化

| 维度 | 云端 API | 本地部署 |
| --- | --- | --- |
| 数据流向 | 请求内容出网 | 全程内网闭环 |
| 内容审核 | 存在策略拦截，安全类任务易被拒答 | 无外部策略干预 |
| 成本模型 | 按 token 计费，长上下文成本高 | 一次性硬件投入 |
| 延迟 | 受网络与限流影响 | 稳定，可预测 |
| 能力上限 | 通常强于同尺寸开源模型 | 取决于本地硬件 |

对安全测试类任务而言，**"请求内容是否离开内网"往往是决策的第一约束**，其次才是模型能力的绝对高低。

## 二、架构分层

```
┌──────────────────────────────────────────────┐
│  编排层  Agent / 自动化框架（规划、工具调用）      │
├──────────────────────────────────────────────┤
│  推理层  推理服务（Ollama / vLLM / llama.cpp）    │
│         暴露 OpenAI 兼容接口 /v1/chat/completions │
├──────────────────────────────────────────────┤
│  模型层  权重文件（GGUF / AWQ / FP8 / BF16）       │
├──────────────────────────────────────────────┤
│  执行层  目标工具（nmap、sqlmap、自定义脚本）        │
└──────────────────────────────────────────────┘
```

**关键设计点**：推理层统一暴露 **OpenAI 兼容 API**，这样上层编排框架只需改 `base_url` 与 `model` 两个字段即可切换后端，不必改代码。这是本地化改造中最省事的一条路径。

## 三、推理服务选型

| 方案 | 优势 | 适用场景 |
| --- | --- | --- |
| Ollama | 安装即用，模型管理方便，自带兼容接口 | 单机验证、个人实验 |
| vLLM | 吞吐高，支持 PagedAttention 与并行 | 多人共用、批量任务 |
| llama.cpp | CPU 可跑，量化友好，资源占用低 | 无独显或显存受限 |
| SGLang | 复杂结构化输出与多轮复用场景表现好 | 高频工具调用 |

个人单机场景建议：**先用 Ollama 跑通链路，再按吞吐需求决定是否迁到 vLLM**。

## 四、模型选型考量

安全类任务对模型的要求与通用对话不同，主要看四点：

1. **长上下文**：日志、响应包、代码片段动辄数万 token，需要 32K 以上，最好 128K；
2. **工具调用（Function Calling）稳定性**：格式化输出能力比"聪明"更重要，格式错一次整条链路就断；
3. **指令遵循与拒绝率**：需要模型在安全的专业语境下保持配合；
4. **中文与代码能力**：中文日志、注释、报告生成的准确度。

参数量与显存的粗略关系（4-bit 量化）：

| 模型规模 | 4-bit 权重占用 | 建议显存 |
| --- | --- | --- |
| 7B / 8B | 约 5–6 GB | 8–12 GB |
| 14B | 约 9–11 GB | 16 GB |
| 32B | 约 19–22 GB | 24 GB |
| 70B | 约 40–45 GB | 48 GB+（或双卡） |

还需为 **KV Cache** 预留空间，上下文越长占用越大。若显存吃紧，优先策略是"降上下文长度"而非"降量化位宽"。

## 五、与编排框架的对接

大多数自动化框架只要求一个 OpenAI 兼容端点，配置形态大致如下：

```bash
# 以 Ollama 为例，先拉取模型
ollama pull qwen2.5:14b-instruct-q4_K_M
ollama serve   # 默认监听 127.0.0.1:11434
```

| 配置项 | 云端 API | 本地 Ollama |
| --- | --- | --- |
| Base URL | `https://api.xxx.com/v1` | `http://127.0.0.1:11434/v1` |
| API Key | 真实密钥 | 任意非空字符串占位 |
| Model | 云端模型名 | `qwen2.5:14b-instruct-q4_K_M` |

**注意**：部分框架要求流式响应或特定的 JSON Schema 输出格式，本地小模型在结构化输出上容易偏差。建议先用最小用例（单轮工具调用）验证连通性，再逐步加大任务复杂度。

## 六、部署注意事项

1. **端口暴露**：推理服务默认只监听 `127.0.0.1`。若容器内访问宿主机，用 `host.docker.internal`，不要图省事绑 `0.0.0.0`；
2. **并发控制**：单卡并发过高会导致显存溢出与响应劣化，需设置并发上限与队列；
3. **超时设置**：本地模型首 token 延迟可能达数秒，客户端超时阈值要相应放大，否则会误判为失败；
4. **日志留存**：推理服务的请求日志包含测试目标信息，属于敏感数据，需纳入内网日志管理；
5. **硬件散热**：长时间满载推理对散热要求高，注意温度墙导致的降频。

## 七、评估方式

不要只看"感觉效果不错"，建议用固定小样本集做回归：准备 20–30 条典型任务（解析扫描结果、生成测试用例、总结日志），每次换模型或调参后重跑，比对**格式正确率**与**结论准确率**两个指标。

## 小结

本地化的核心收益是**数据主权与可控性**，代价是模型能力上限与运维成本。工程上的关键是选一个**兼容 OpenAI 接口的推理后端**，把模型选择变成一个可替换的配置项，而不是与架构绑死的硬依赖。
