# SQL 注入：从原理到防御的完整链路

> SQL 注入（SQLi）长期位居 OWASP Top 10 前列，其本质不是"数据库漏洞"，而是**应用层把用户输入当成了代码**。

## 一、根本成因

程序将外部输入直接拼接进 SQL 语句，使数据与指令的边界被打破：

```php
// 反例：字符串拼接
$sql = "SELECT * FROM users WHERE name = '" . $_GET['name'] . "'";
```

当输入为 `admin' --` 时，语句结构被篡改，后续条件被注释掉。

**核心判据**：只要"拼接"存在，就存在注入面。参数化查询之所以安全，是因为它在协议层把查询模板与参数分离传输，数据库引擎不会再对参数做语法解析。

## 二、注入类型分类

| 类型 | 特征 | 典型回显表现 |
| --- | --- | --- |
| 联合查询注入 | 使用 `UNION` 拼接结果集 | 页面直接回显其他表数据 |
| 报错注入 | 借助数据库报错信息带出数据 | 页面返回 SQL 错误栈 |
| 布尔盲注 | 仅通过真假响应差异判断 | 页面内容长度/文案变化 |
| 时间盲注 | 通过响应延迟判断 | 无回显、无差异，仅有延时 |
| 堆叠注入 | 分号后追加新语句 | 通常需驱动支持多语句 |

## 三、注入点识别思路

1. **数字型与字符型**：数字型无需闭合引号，字符型需匹配引号与括号层级。
2. **判断列数**：`ORDER BY n` 递增法，或用 `UNION SELECT 1,2,3...` 逐步试探。
3. **判断回显位**：确定结果集中哪些列会被渲染到页面上。
4. **判断数据库类型**：MySQL、MSSQL、Oracle、PostgreSQL 的报错特征与系统表各不相同。

常见的注入位置远不止 GET 参数：HTTP 头（`User-Agent`、`Referer`、`X-Forwarded-For`）、Cookie、JSON Body、排序字段、分页参数、以及被写入日志后再被查询的二次注入点。

## 四、纵深防御清单

### 1. 代码层（最关键）

```java
// 正例：预编译参数化
String sql = "SELECT * FROM users WHERE name = ?";
PreparedStatement ps = conn.prepareStatement(sql);
ps.setString(1, name);
```

- 所有 SQL 一律走参数化 API，禁止拼接；
- 表名、列名、排序方向等**无法参数化**的部分，采用**白名单枚举**映射；
- 使用 ORM 时注意 `raw()` / `query()` 等逃逸口，它们不会自动参数化。

### 2. 数据库层

- 业务账号遵循**最小权限**：只授予 `SELECT/INSERT/UPDATE/DELETE`，禁止 `FILE`、`DROP`、跨库访问；
- 关闭 `xp_cmdshell`（MSSQL）、禁用 `LOAD_FILE`/`INTO OUTFILE`（MySQL）等危险能力；
- 开启详细日志但**禁止回显到前端**，报错信息统一转换。

### 3. 架构层

- Web 与数据库之间可加一层数据访问代理做语句模板校验；
- WAF 仅作为**兜底而非主力**，正则规则容易被编码绕过（大小写、注释、内联注释、宽字节、Unicode）。

## 五、验证与回归

修复后必须复测的三种形态：原始 payload、编码变体、以及同参数在其他请求方法（POST/PUT/JSON）下的表现。建议把每一个历史漏洞点沉淀为自动化用例，纳入 CI。

## 小结

参数化查询解决了 90% 的问题，剩下的 10% 靠**输入白名单**与**最小权限**兜底。任何依赖"过滤黑名单"的方案，长期看都会失守。
